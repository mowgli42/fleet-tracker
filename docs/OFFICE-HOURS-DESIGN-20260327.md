## Problem Statement
Build a demo that proves a local shop can keep maintenance operations running during cloud outages, while still giving an owner trustworthy cross-site availability once connectivity returns.

The core user is a shop owner who needs confidence that no maintenance-critical vehicle is silently missed when sites disconnect.

## What Makes This Cool
- Real "cloud down, shop still works" behavior, not a mocked spinner.
- Cross-site transfer works even when destination is offline: vehicle shows in-transit, then lands automatically on reconnect.
- Owner sees a clean readiness signal across sites: ready, at-risk, blocked, with no manual reconciliation.

## Constraints
- Demo scope must cover all three surfaces, but thinly: cloud app, local containerized shop node, and connected workstation/tablet client.
- Intermittent connectivity is a first-class scenario, not an edge case.
- Existing prototype should be reused where possible; avoid a full rewrite.
- Learning-mode timeline: optimize for a coherent demo wedge over full product completeness.

## Definitions (for demo acceptance)
- **Ready**: vehicle has no active maintenance blocker and no overdue PM threshold breach.
- **At-risk**: vehicle has a PM due within threshold window (for demo: due within 7 days or 300 miles).
- **Blocked**: vehicle has active maintenance job with blocking severity or transfer unresolved beyond SLA.
- **Converged global state**: cloud projection matches all site event logs with zero pending outbox events.
- **Exactly once (user-visible)**: duplicate replays do not create duplicate state transitions in owner UI.

## Premises
1. Hero flow is maintenance-first operational availability, not check-in-first.
2. Local shops continue operating during cloud outage, then sync back.
3. Site transfer to offline destination queues as in-transit and auto-applies on reconnect.
4. Shop owner view must show ready / at-risk / blocked across sites without manual reconciliation.

## Approaches Considered
### Approach A: Cloud-Primary with Local Cache
Summary: Keep cloud as source of truth and use local cache + queued writes during outages.

- Effort: Small
- Risk: High for outage trust
- Pros: fastest implementation, minimal architecture change
- Cons: weak offline guarantees, brittle conflict behavior, owner trust risk
- Reuses: current store/view patterns with queue wrapper

### Approach B: Local-First Event Log + Cloud Projection (Chosen)
Summary: Each site writes local append-only events, cloud asynchronously projects global availability.

- Effort: Medium
- Risk: Medium
- Pros: strong offline behavior, explicit conflict policy, durable audit trail, best fit for "no missed jobs"
- Cons: event envelope + projector complexity, requires idempotency discipline
- Reuses: existing domain/status model and dashboard aggregation concepts

### Approach C: Multi-Master Document Sync
Summary: Sites and cloud co-edit mutable records directly with merge metadata.

- Effort: Large
- Risk: Medium-high
- Pros: elegant long-term distributed editing
- Cons: too heavy for current demo, harder to explain quickly
- Reuses: mainly domain entities only

## Recommended Approach
Choose Approach B.

It gives the best reliability-to-complexity ratio for this demo. The owner value depends on truth under failure, and local-first event capture is the cleanest way to preserve that truth. Cloud projection provides consistent multi-site visibility without blocking shop operations.

## Technical Spec (Demo-Level)
### Event envelope (minimum)
- `event_id` (UUID)
- `site_id`
- `entity_type` (`vehicle`, `maintenance_job`, `transfer`)
- `entity_id`
- `event_type` (`maintenance_blocked`, `maintenance_cleared`, `pm_risk_set`, `transfer_created`, `transfer_applied`)
- `event_ts_local`
- `event_ts_server` (nullable until synced)
- `actor_id`
- `idempotency_key`
- `causal_version` (monotonic per entity at site)
- `payload` (JSON)

### Sync protocol
1. Site app writes to local event log.
2. Outbox worker posts unsynced events to cloud `/sync/events`.
3. Cloud acknowledges accepted events with ack cursor and rejects with reason.
4. Site marks acked events as synced and retries rejected events by policy.
5. Cloud projector updates owner read model by deterministic projection functions.

### Failure and retry policy
- Retry: exponential backoff (1s, 2s, 4s, capped at 60s).
- Replay safety: cloud dedup by `idempotency_key`.
- Partial failure: keep unsynced events queued, never drop local events automatically.

### Conflict policy (resolved now)
- Default: deterministic precedence = latest `event_ts_server`; tie-break by `site_id` lexical order.
- Manual override UI is out-of-scope for demo; conflicts are logged for visibility.

## Non-Functional Targets (Demo)
- Supports local operation with cloud outage up to 8 hours.
- Reconnect convergence target: < 3 minutes for <= 5,000 queued events.
- Data loss tolerance: zero lost accepted local events.
- Transfer application SLA after reconnect: < 60 seconds.

## Scope Phasing
### Phase 1 (must ship)
1. Single-site local operation during cloud outage.
2. Event outbox + replay + cloud projection for availability statuses.
3. Owner dashboard showing Ready / At-risk / Blocked from projected state.

### Phase 2 (if time)
1. Cross-site transfer to offline destination with in-transit state.
2. Auto-apply on destination reconnect.
3. Cross-site owner convergence visualization.

## Out of Scope (explicit)
- Full RBAC/auth hardening.
- Multi-region cloud deployment.
- Manual conflict resolution workflow UI.
- Rich tablet-native app packaging (PWA is sufficient).
- Billing/tenant monetization features.

## Open Questions
1. Should at-risk threshold be configurable per site in demo, or global constant only?
2. Should blocked include parts-waiting state automatically, or only explicit blockers?

## Success Criteria
1. During simulated cloud outage, local site can create/update maintenance events.
2. Local owner/site availability remains correct (ready/at-risk/blocked).
3. On reconnect, all queued events apply idempotently (no duplicate state transitions).
4. (Phase 2) Offline-destination transfer auto-applies when destination reconnects.
5. Cloud owner dashboard converges to projected truth without manual reconciliation.

## Test Matrix (must exist for demo credibility)
- **Contract tests**: event envelope validation and sync endpoint responses.
- **Replay/idempotency tests**: duplicate post of same event_id/idempotency_key.
- **Conflict tests**: concurrent updates to same vehicle from two sites.
- **Outage tests**: cloud down for 30+ minutes, then recover and converge.
- **Projection tests**: event streams produce expected readiness class.

## Distribution Plan
- Cloud demo: hosted service exposing sync + owner read model APIs.
- Local shop demo: Docker Compose node with local event store and sync worker.
- Client demo: browser/PWA app for workstation/tablet using local-first adapter.
- CI/CD:
  - Build/publish local node image.
  - Deploy cloud service on demo branch merge.
  - Run outage + replay smoke suite in CI.

## Risks and Mitigations
1. **Replay bugs create phantom state**
   - Mitigation: strict idempotency keys + replay tests before demo cut.
2. **Projection lag confuses owner view**
   - Mitigation: expose projection lag metric and pending-event badge.
3. **Scope creep across three surfaces**
   - Mitigation: enforce Phase 1 cutline as non-negotiable demo baseline.

## Next Steps
1. Define and implement event schema + sync contract.
2. Build site-local event store + outbox worker.
3. Build cloud projector + owner availability read model.
4. Implement outage simulation harness and scripted demo path.
5. Add phase-gated transfer flow (Phase 2 only after Phase 1 passes).

## What I noticed about how you think
- You started broad, then tightened fast to an owner-visible outcome: "no missed maintenance jobs, even with flaky internet."
- You corrected scope when it drifted, from check-in-first to maintenance-first, which is exactly the right product move.
- You anchored constraints in reality: existing software fails when disconnected and cannot move vehicles across sites.
- You picked a trust-critical failure mode (cloud unreachable while shops keep working), not a cosmetic edge case.

### AI slop and layout rules (APP UI)

- **Avoid:** generic three-column feature grids, purple gradients, decorative icon circles, marketing hero on internal dashboards.
- **Prefer:** calm surfaces, strong type, one accent (`--color-accent` family), sections titled by **job** (“Blocked now”, “Pending sync”), cards only when the card is the interaction (panels, job editor), reuse **StackedBar**-style summaries for categorical counts.
- **Litmus (target):** Headlines alone communicate page purpose; motion only for sync feedback or timeline playback (Phase 2), not decoration.

### Design system alignment (fleet-tracker reuse)

There is **no** top-level `DESIGN.md` in the repo; **source of truth for the current app** is `src/app.css` (CSS variables, DM Sans + Sora, sidebar shell, skip link).

**Reuse for demo surfaces:**

- **Typography:** Sora for headings and chrome, DM Sans for body (already loaded).
- **Color:** `--color-accent`, `--surface-dark`, `--border-subtle`, status via existing badge patterns (extend semantically for Ready / At-risk / Blocked rather than inventing a second palette).
- **Components/patterns:** `StackedBar` for aggregate readiness; slide or explicit confirm for destructive actions; panels for edit flows (match `*EditPanel` patterns).
- **New UI for this demo** should extend this vocabulary. If the demo ships as a separate shell, fork tokens from `app.css` into a short `DESIGN.md` in the demo package when it diverges.

### Responsive and accessibility (targets)

- **Breakpoints:** Collapse sidebar to top or icon rail under `md`; maintain single primary column for task lists on tablet.
- **Touch:** Minimum **44px** hit targets on tablet paths; slide-to-confirm affordances must have keyboard alternative (already a pattern to mirror from fleet-tracker).
- **Keyboard:** Logical tab order in panels; focus traps in modals; skip link to main content on each shell.
- **Screen readers:** Live region or polite announcement for **sync state changes** and **convergence complete** (avoid silent updates).
- **Contrast:** Status colors must pass WCAG AA for text on chosen backgrounds; do not rely on color alone (pair with icon or label).

### Step 0: Scope challenge

1. **Existing code:** `src/lib/stores/fleetData`, SvelteKit routes (`/`, `/fleet`, `/maintenance`, parts), UI patterns in `src/app.css` and components. The demo should **evolve** this domain model into an event-sourced pipeline, not fork a second app in parallel. Minimum change set: introduce **local event log + outbox** behind the same entities, then cloud projector and owner API.
2. **Minimum to hit the goal:** Phase 1 only until acceptance: single site, outage, replay, owner projection. Phase 2 transfer stays gated.
3. **Complexity:** Three deployables (cloud, local node, PWA) are required by the problem statement. Keep **one shared contract** for events and availability math (`TODOS.md` P1) to avoid two divergent implementations.
4. **Search / boring tech:** Prefer SQLite or embedded store + HTTP for local node over exotic databases. Use backoff libraries you already trust; avoid custom consensus.
5. **TODOS cross-reference:** P1 shared derivation contract is **blocking** for trustworthy Ready/At-risk/Blocked. New P2 items from design review (DESIGN.md when diverged, owner copy) are **not** blocking Phase 1 code, but block a polished demo narrative.
6. **Completeness:** Treat `docs/TEST-PLAN-OFFLINE-SYNC.md` as binding for CI; anything in the matrix without a test is incomplete for demo credibility.
7. **Distribution:** Plan already lists Compose image and CI smoke; **do not** ship code without a published image path or documented `docker compose up` for evaluators.

### Architecture

**End-to-end data flow (Phase 1):**

```
[Shop UI] → validate → append Event → [Local event log] → [Outbox worker] --POST--> [Cloud /sync/events]
                                                              |                      |
                                                              v                      v
                                                       retry/backoff           dedupe + order
                                                                                      |
                                                                                      v
                                                                              [Cloud projector]
                                                                                      |
                                                                                      v
                                                                              [Owner read model API]
                                                                                      |
                                                                                      v
[Owner UI] <----------------------- read --------------------------------------------+
```

**Single point of truth for “what the vehicle status is”:** one **pure projection** from ordered events, shared contract for local preview and cloud (see `TODOS.md` P1).

**Conflict and ordering:** The plan’s “latest `event_ts_server` + lexical `site_id`” must be reconciled with **`causal_version` per entity at site** in the envelope. Until synced, `event_ts_server` is null — **do not** pretend wall-clock ordering exists pre-sync. Recommendation: **document one precedence ladder** (for example: causal_version first for same entity, then server time when present, then tie-breakers) and add **one** golden test file that encodes it so Phase 1 and cloud never disagree.

**Security (demo minimum):** `/sync/events` needs at least **site-scoped credentials** (API key or signed token per site). “No RBAC” does not mean “open POST from the internet.”

### Code quality and boundaries

- **DRY:** Event schema types and projection functions should live in a **shared module** consumed by site app, cloud projector, and tests. Avoid copy-paste enums.
- **Explicit errors:** Sync reject reasons must be structured (code + message) so the outbox can retry vs dead-letter without guessing strings.
- **SvelteKit today:** In-memory JSON store is fine for prototype; migration path is **adapter** that turns UI actions into events instead of mutating store in place, then projector fills read models.
